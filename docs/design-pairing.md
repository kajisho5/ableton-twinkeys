## 1. 目的

今は、同じネットワーク上で TwinKeys として見えていれば、どの機器でもつなげてしまう（0.4.x の残課題）。次の3つを防ぐ。

1. 知らない機器がメインの Mac につなぎ、打鍵（17文字分）を音として受け取る
2. バックアップ機になりすまして、接続を乗っ取る、または音を送り込む
3. 通信を盗み見る、または前に流れた通信を再送する

あわせて、Bonjour（自動で相手を探す仕組み）が届かないネットワークでもつなげるように、IP アドレス指定の接続を足す。

## 2. 使い方（利用者から見た流れ）

1. 片方の Mac の「設定」>「合言葉」で「新しく作る」を押すと、10文字の合言葉（例 `K7MQ2-WX9TP`）が出る
2. もう片方の Mac で「合言葉を入力…」を押し、同じ10文字を入れる
3. あとは今までどおり「接続」を押す。合言葉は保存されるので、次からは入力不要
4. 合言葉が違う相手は、一覧に「合言葉が違います」と出て、つながらない
5. 一覧に相手が出ないとき（会場の Wi-Fi など）は、「IP アドレスで接続…」（⇧⌘K）から相手の IP を入れる。相手の IP は、相手側の「設定」>「合言葉」に表示される

合言葉が未設定のあいだは接続できない。メイン画面の上に案内を出す（`pairing-main-*.svg`）。

## 3. 画面（`docs/design/pairing-*.svg`、ライト／ダーク）

| ファイル | 内容 |
|---|---|
| `pairing-main-*` | 合言葉が未設定のときの案内、合言葉が違う相手の表示、「IP アドレスで接続…」ボタン |

## 4. 暗号の仕組み

部品：Apple 公式の **swift-crypto 5.1.1**（`Crypto`）を使う。Mac では OS の CryptoKit がそのまま使われ、Linux でのテストでは同じ API の実装が使われる。暗号は自作しない。**[事実]** https://github.com/apple/swift-crypto

### 4.1 合言葉

- 紛らわしい文字（0/O、1/I/L など）を除いた31種類の文字で10文字を作る。強さはおよそ 49 ビット
- 比べる前に、大文字に変え、空白とハイフンを除く
- 合言葉から長期の鍵 K を作る：PBKDF2-HMAC-SHA256、10万回、salt は固定文字列 `"TwinKeys pairing v2"`。1回の推測に時間がかかるので、盗み見た通信から合言葉を総当たりで割り出すのは現実的でなくなる（10文字 × 10万回 ≒ 2^66 回の計算）。PBKDF2 は swift-crypto の HMAC で書き、RFC 7914 のテスト値で確かめる **[事実]** https://www.rfc-editor.org/rfc/rfc7914#section-11
- K は Mac のキーチェーンに保存する。設定ファイル（settings.json）には書かない

### 4.2 接続のあいさつ（Hello / HelloAck）

- それぞれの Mac は、起動するたびにランダムな 16 バイト（boot nonce）を作る
- Hello と HelloAck には、送り手の boot nonce を入れ、パケット全体を **HMAC-SHA256(K)**（先頭 16 バイト）で署名する
- 署名が合わないあいさつは捨てる。そのうえで「合言葉が違う相手」として一覧に印を付ける（Bonjour で見えている相手のときだけ）

### 4.3 つながったあとの通信

- 向きごとの鍵：送り手 → 受け手 の鍵 = HMAC-SHA256(K, `"dir"` ‖ 送り手 nonce ‖ 受け手 nonce)
- ノート・ハートビート・Held・Bye・オールノートオフは、すべて **ChaCha20-Poly1305** で暗号化して改ざんを防ぐ。12 バイトのヘッダーは AAD（暗号化はしないが改ざん検知に含める部分）にする。nonce は 送り手 session(4) ‖ seq(4) ‖ 0(4)。同じ番号で 2 回送るときは中身も同じなので、nonce の使い回しによる弱点は生まない
- 起動するたびに鍵が変わるので、前に流れた通信を再送しても受け付けない。同じ起動の中の再送は、今の順番チェック（seq）で捨てる

### 4.4 パケットの形（プロトコル版 2）

```
ヘッダー 12B：'T' 'K' | version=2 | type | session u32 | seq u32
Hello / HelloAck：id 16B | nonce 16B | name len + UTF-8 ≤32B | HMAC 16B
その他：ChaCha20-Poly1305 の暗号文（中身は版 1 と同じ） | tag 16B
最大 128B
```

### 4.5 これで防げること／防げないこと

| 攻撃 | 結果 |
|---|---|
| 知らない機器がつなぐ・音を受け取る | 防げる（合言葉がないとあいさつが通らない） |
| なりすまし・乗っ取り・音の送り込み | 防げる |
| 盗み見（どのノートを弾いたか） | 防げる（暗号化） |
| 再送 | 防げる（起動ごとの鍵と順番チェック） |
| 大量のパケットを送りつける | 署名の確認で捨てる。ログは今と同じく1分に1回に絞る |
| 合言葉そのものが漏れた | 防げない。「新しく作る」で作り直す |

0.4.x で入れた「Bonjour で見えている相手だけ受け付ける」制限は外す。確かめる役目は合言葉が担う。そうしないと IP 指定の接続ができないため。

## 5. IP アドレス指定の接続

- 待ち受けのポートを **47801/UDP に固定**する。使えないときは OS が選んだポートを使い、その旨を画面に出す
- 「IP アドレスで接続…」に入れた IP（IPv4 か IPv6）の 47801 へ Hello を送る。相手の ID は HelloAck で分かる
- 最後に使った IP は保存し、次からの候補に出す
- Bonjour で見つかる相手は、今までどおり一覧から接続できる

## 6. 実際のネットワークでの見込み

| つなぎ方 | 見込み |
|---|---|
| ルーター（DHCP あり） | 動く |
| LAN ケーブル1本で直結 | Mac が仮の IP アドレス（169.254.x.x）を付け、Bonjour も動くはず **[推測。実機で確認]** |
| 会場の Wi-Fi（機器どうしの通信を止める設定） | Bonjour も IP 指定も届かない。有線か、専用のルーターを使う |
| Bonjour だけ止められているネットワーク | IP 指定でつなげる |
| ネットワークが2つに分かれている（VLAN など） | IP 指定でつなげる（ルーターが通す設定なら） |
